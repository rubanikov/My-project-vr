# Court Clash (working title) — Product Requirements Document

Written for the Claude Code session working directly in this Unity project. This file is self-contained — it's the single source of truth for what to build. Don't look for or infer requirements from anything outside it.

## Overview

A standing, grounded VR game for Meta Quest 2. It's a 1v1 sport played inside a small court with multi-faceted geometric walls (visually inspired by Echo VR's field, not its zero-g movement). Instead of swinging a racquet, the player grabs and throws a large ball. The court's walls are angled, so the ball bounces around unpredictably. A single AI opponent plays the other side. Fault rule: if the ball bounces more than once before being returned, the point/rally is lost.

## Core mechanics

### Court
- Multi-faceted geometric walls (not a simple 4-wall box) — angled surfaces so ball bounces are varied and interesting.
- **Procedurally sized to the player's real Quest Guardian boundary at game start**, using `OVRBoundary.GetDimensions()` (Meta's Integrate Boundary API), so the court always fits the player's actual room. This is a real, documented API — not a novel technique.
- Grounded — the player stands and steps within this bounded space; no locomotion system needed.

### Ball throw
- A single large ball, grabbable and throwable using standard VR grab-and-throw interaction (Touch controller velocity on release).
- Bounces off walls/floor using Unity's built-in physics (Rigidbody + a bouncy PhysicMaterial) — this should not require custom bounce-reflection code, just correct physics material/collider setup.
- Use continuous collision detection on the ball's Rigidbody to avoid tunneling through thin wall geometry at speed.

### Fault rule ("no more than one bounce")
- Track bounce count on the ball since it was last thrown/touched by a side.
- If the count exceeds the limit before the opposing side touches/catches it, that's a fault — award the point/rally to the other side.
- **Open question, needs a decision before this is built**: does the counter reset every time a side catches and re-throws (a strict "each throw gets one bounce" rule), or is it a running count across a longer rally? Floor bounces and wall bounces — treated the same, or differently? Pick a reasonable default, implement it, and flag it clearly so it can be adjusted once it's actually felt in play.

### AI opponent
- Predicts the ball's trajectory from its current velocity and gravity (standard physics extrapolation — not pathfinding, not exotic).
- Moves to an intercept point in time to catch the ball.
- Throws back, ideally aiming for gaps in the player's position rather than straight back (can start simple — random aim within a cone — and improve later).
- This is the most interesting system in the project; it's expected to take real iteration.

## Explicitly out of scope

- Zero-g locomotion (the court is grounded/standing).
- Real multiplayer/networking — the opponent is AI, never a networked human.
- External hardware controllers (HOTAS/flight sticks) — not relevant to this game.
- A full narrative/companion system. An evolving AI rival personality (Convai-voiced banter reacting to score) is a **stretch goal only** — do not build it before the core loop (court, throw, bounce, fault rule, AI opponent) is playable and demoable.
- Manual 3D modeling/animation — use simple primitive geometry or AI-generated assets rather than hand-authoring art.
- Publishing/app store submission, monetization.

## Recommended build order

1. Confirm setup: Meta XR SDK present, MCP bridge live, project builds and deploys to the Quest 2 (sanity check before building features).
2. Court geometry + Guardian-boundary sizing.
3. Ball: grab/throw interaction + wall/floor bounce physics + the fault-rule logic.

**Testing gotcha worth knowing**: don't set a non-kinematic `Rigidbody`'s position via `transform.position = ...` in a test script — the physics engine doesn't reliably sync it same-frame, so `Rigidbody.position` (what gameplay code actually reads) can stay stale or behave unpredictably. Use `rb.position = ...` instead. Also, two separate `Unity_RunCommand` calls are not "the same instant" — real Play-mode time (a few seconds, empirically) passes between them from ordinary tool round-trip latency, which is enough for several physics bounces or a full AI movement step. Set `Time.timeScale = 0f` immediately after setting up a test state if the check needs to see it before anything else can react, and restore it to `1f` afterward.

**Real Quest 2 hardware testing (2026-08-26) — crash found and fixed.** First on-device build (Build-and-Run via `BuildPipeline.BuildPlayer`, installed/launched via the `metavr` MCP tools over USB) crashed a few minutes into play. Root cause, confirmed via the device's dedicated crash log buffer (`adb logcat -b crash`, not the noisy main buffer which rolls over in a couple of minutes under VR's log volume): `libc: mprotect failed on atexit array: Out of memory`, `Fatal signal 6 (SIGABRT)`, ~930MB peak RSS. Direct cause: the AI-generated robot/hand meshes from the previous session (`AIRobot.prefab`, `PlayerHand2.prefab`) were ~730-770k vertices *each*, rendered in stereo — the AI mesh-generation pipeline (`GenerateMesh`/`model3d-tripo3-1`) produces far more geometry than a Quest 2 can hold, let alone render in real time. The user's own live symptoms before the crash (view flickering/shaking once the headset moved, tracking appearing frozen, controller movement having no visible effect) were the same GPU/memory overload manifesting as broken frame delivery, not a separate bug.

Fix: Unity AI's `RetopologyMesh` command (model `model3d-tripo-retopo`) decimates an existing mesh to a real-time-safe polycount while rebaking its texture — requires the `com.unity.cloud.gltfast` package (not installed by default; added via `Unity_PackageManager_ExecuteAction`, exact version had to be pinned since `"latest"` isn't a valid version range for that tool). Also: this command rejects a `prompt` argument outright (`ArgumentException: A 'prompt' cannot be used when retopologizing a mesh` — unlike every other `GenerateAsset` command, it takes no tuning parameters, just `targetAssetPath`). `AIRobot.prefab` retopologized cleanly in ~2 minutes: 768k → **16.6k vertices**. `PlayerHand2.prefab`'s retopology job tripped the same internal 10-minute safety-net warning seen once before in this project (`GenerateAsset] Timeout safety net tripped (UUM-144682)`) and was still running 20+ minutes later ("continues in the background" per Unity's own log) — user chose not to keep waiting. **Current state**: both `RightHandVisual`/`LeftHandVisual` were swapped from the oversized mesh prefab to plain low-poly `Capsule` primitives (collider removed, `PlayerRobotShellAI.mat` applied) as an interim fix — visually plainer than the intended articulated hand mesh, but functionally fine. If `PlayerHand2.prefab`'s retopology job ever completes server-side, it can be swapped back in the same way `AIRobot_Visual` was integrated (see above).

Also found on real hardware, unrelated to the crash: `OVRManager.trackingOriginType` was `EyeLevel` (0) instead of `FloorLevel` (1) — meant the player's rendered view sat well below their actual standing height, since Eye Level tracking doesn't use real floor-relative height data. Fixed by setting it to `FloorLevel` (1) via `set_component_property` on the `OVRCameraRig`'s `OVRManager` component.

**Racket mechanic replaces grab-and-throw (2026-08-26, overnight, user asleep — not yet human-tested)**: user asked for something more dynamic than grab-hold-release, and for the ball 50% smaller. Implemented:
- **`Assets/Scripts/PlayerRacket.cs`** (new) — a kinematic paddle (`Racket` GameObject) parented to `RightControllerAnchor` only (single-handed, right hand — no left-hand racket). Each `FixedUpdate` it `MovePosition`/`MoveRotation`s to the controller anchor's pose. `OnCollisionEnter` checks `collision.rigidbody == ball` (direct reference, no tag needed) and calls `ballFaultTracker.NotifyTouched(Side.Player)` + `matchController.OnBallInPlay()`. **Correction (2026-08-26, later same night)**: the original version of this also assigned the anchor's frame-to-frame position delta directly to the kinematic `Rigidbody.linearVelocity`, on the assumption PhysX needs that explicitly set to compute collision response. Wrong — Unity logs "Setting linear velocity of a kinematic body is not supported" and silently no-ops it every `FixedUpdate` (found via a console warning during testing, would never have surfaced from behavior alone since the ball still bounced off a *stationary* racket fine in every test up to that point). `MovePosition`/`MoveRotation` alone already carry the correct implicit velocity for PhysX collision response — the same mechanism a moving platform uses to push a character. Removed the dead velocity-assignment code entirely. Also set the Racket's `Rigidbody.collisionDetectionMode` to `ContinuousDynamic` (matching the ball's own setting) so a fast real swing can't tunnel straight through the now much-smaller ball without registering a hit.
- **`BallFaultTracker.cs`** — `OnCollisionEnter` (used for wall/floor bounce counting) now skips `RegisterBounce()` when the collision partner has a `PlayerRacket` component, since `PlayerRacket`'s own handler already calls `NotifyTouched` for that same physical collision — without this, a racket hit would get double-counted as both a touch *and* a bounce in the same physics step.
- **`MatchController.cs`** — `OnBallGrabbed()` renamed to `OnBallInPlay()` (match now starts on the player's first racket-ball contact instead of first grab — same one-trigger-for-the-session idea, just re-anchored to the new interaction).
- **`Assets/Scripts/PlayerBallGrab.cs`** — deleted (fully superseded).
- **Ball**: `localScale` halved from `0.22` to `0.11` (also updated `BallSetup.cs`'s `BallDiameter` constant for consistency, though that editor script only runs once at initial setup — the live scene object was resized directly).

1. **Weak-hit root cause found and fixed — a real bug, confirmed by inspection**: the `Racket` was BOTH parented under `RightControllerAnchor` (scene) AND `MovePosition`'d to that same anchor every FixedUpdate (`PlayerRacket`). **Court-vs-boundary misalignment fixed + walls to ceiling (2026-08-26, user: large play area but "only a small portion of it was in my half... most of the play guard was outside the court... the court seems to be the same size no matter the boundary")**: root cause was NOT wall sizing (walls always scaled) — the court was being built around the WORLD ORIGIN, which with FloorLevel tracking is the player's recenter point, while only the play area's SIZE was read (`GetDimensions`). A player launching near the corner of a large room got a correctly-sized court planted around themselves, mostly outside the real play area. Fix, verified against Meta's Integrate Boundary docs: read `OVRBoundary.GetGeometry(BoundaryType.PlayArea)` — corner points in tracking space, carrying position AND size (not deprecated; only OuterBoundary/TestNode/etc. are) — take the AABB, and build the whole court centered on the play area (`CourtBuilder.CenterX`, net at the area's front edge). Dimensions-only remains as a secondary fallback (centered on player, logged), fixed 2.5m fallback last. A `[CourtBuilder] Building court. realBoundary=... playAreaCenter=... halfExtents=...` Debug.Log now records which path ran — grep device logcat for "CourtBuilder" to finally confirm whether real boundary data is used on-device (the PRD has flagged that path as never-confirmed since day one; the "same size every launch" symptom suggests it may always have fallen back). Consumers updated for CenterX: AIOpponent (home/clamps/targets), Scoreboard, and MatchController's ball pedestal (now recomputed to the middle of the player's half on CourtBuilt). **Walls raised to the full 4m ceiling height** (user request; also kills the visible open band — the invisible extension panels auto-skip now that the band is zero). Editor XR-teardown crash struck AGAIN on Stop-Play (third time, same OpenXR deinit stack) — relaunched, no data lost; editor Play verification skipped this round in favor of on-device logcat verification, which is the environment the bug actually lives in.

**Pause/reset + serve let + score-jump fixes (2026-08-27, user: pause/start/reset request; "the score jumps around... 1-0 to 3-0 to 8-3"; "if the player serving does not hit the ball and it drops, don't count it — let him serve again")**: three score-jump sources identified and fixed, plus the requested controls:
1. **Serve Let** (`FaultKind.ServeLet`, `PadelRallyRule.HitCount`): a rally's FIRST hit failing to clear the net is a let — no point, the same side re-serves (1s pause, `MatchController.ReServeAfterPause`). Applies to the AI's serves symmetrically. This also kills the biggest point-drain: the ball resets right in front of the player, and any accidental racket touch that dribbled to the floor was an instant FailedClear point to the AI. Mid-rally failed clears still cost the point; a serve that clears but goes unreturned still scores normally. 4 new EditMode tests + inline checks all pass.
2. **Between-rally fault gate**: `MatchController.OnFault` ignores faults while the rally-flow pause coroutine is active — previously, poking the dead ball during the 1.5s pause revived the rally (RegisterHit) and could instantly fault again, stacking extra points.
3. **Point announcements**: every point now flashes who won it and why on the scoreboard ("POINT: YOU — DOUBLE BOUNCE" / "INTO THE NET" / "BODY HIT"; lets show "FAULT SERVE — SERVE AGAIN"), because silent instant faults made even legitimate scoring read as random jumps. New `MatchController.PointDetail`/`ServeLetOccurred`/`MatchReset` events.
4. **Pause/reset controls** (`MatchPauseController.cs`, on the MatchController object): LEFT controller MENU button (`OVRInput.Button.Start` — the only app-usable system button) toggles pause via `Time.timeScale = 0` (physics, AI, coroutines, and the player's physics-driven racket all freeze; OVRInput keeps polling so resume works); while paused, B (right controller) calls `MatchController.ResetMatch()` (0-0, idle, player serve) and resumes. Scoreboard shows "PAUSED — (B) RESET MATCH · (MENU) RESUME" while paused. `OnDisable` restores timeScale as a safety.

**Playtest-feedback batch: lost-ball recovery, dead-ball rule, referee voice, ball-speed slider, start screen (2026-08-27, user: "the ball disappears some times", "hard to know when someone won a point", "seems like the ball bounces several times and the game still goes on", voice/slider/start-screen requests)**: the two rally bugs share one root — once the ball tunnels out of the court shell nothing it touches is `CourtFloor`, so no fault can fire: the ball is gone AND the rally hangs. A second hang: a ball that settles into ROLLING after one legal bounce keeps floor contact, so `OnCollisionEnter` never reports the second bounce. Fixes and features:
1. **`BallEscapeWatchdog`** (new, on the ball): outside the built court (± 0.75m margin) or under the floor for 0.6s continuous → `MatchController.RecoverEscapedBall()`: void rally, no point, re-serve the same side (idle: just reset to pedestal). Scoreboard flashes "BALL LOST — RE-SERVING" via the new `BallRecovered` event.
2. **Dead-ball rule** (`PadelRallyRule.RegisterDeadBall` + watchdog in `BallFaultTracker.Update`): live rally, ≥1 bounce, ball below 0.35m and slower than 0.8 m/s for a continuous second → same fault as a double bounce (point to the last toucher). 3 new EditMode tests.
3. **Referee voice** (`MatchAnnouncer`, new "Announcer" object): speaks every point from the player's perspective — "you win the point" / "you lose the point" — on `PointScored`. 2D deliberately (a referee in your ear, not a court object). Clips are local Windows-TTS WAVs (`VoiceWinPoint/VoiceLosePoint.wav`, see Assets/Audio/CREDITS.md).
4. **Ball Speed slider** (`BallPhysicsTuning.SpeedMultiplier`, Immersive Debugger "Ball Physics" panel, 0.4–1.5): scales the player's hit exit speed directly; for the AI it stretches shot flight time instead (`flightTime / multiplier`), so the ballistic solve still lands on the chosen target — slower = loopier, same aim.
5. **Start screen** (`StartScreen`, new object; `MatchController.SessionArmed` gate): a panel over the net (scoreboard's TextMesh idiom + same panel material) shows the full control map at launch, after every match, and on reset; racket-ball contact is inert until RIGHT TRIGGER arms the session — warm-up swings can't start a match. Scoreboard idle/rematch texts updated to point at the trigger.
Wiring: new one-click menu item **Court Clash/Setup Feedback And Start Screen** (companion to Setup Ball In Scene). Components self-find scene refs at runtime; the menu item only adds them and assigns assets.

**Anti-tunnel physics hardening (2026-08-27, follow-up — user: "do we have Enable CCD or any other options... like thick colliders?")**: audit found ball CCD already `ContinuousDynamic` (BallSetup) and 90Hz physics already set, but three gaps, all closed:
1. **Racket CCD**: the kinematic racket Rigidbody was `Discrete` — the fastest object in the game had no continuous collision at all. Now `ContinuousSpeculative` (the only continuous mode kinematic bodies support), set in `PlayerRacket.Awake`.
2. **Shell thickness**: walls/floor/ceiling were 0.1–0.15m — LESS than one 90Hz step of ball travel at the 15 m/s cap (~0.17m), and depenetration can eject through anything thin. All shell colliders are now `wallThickness` = 0.5m, grown OUTWARD (every inner face stays at the court edge — playable space unchanged; note the scene's serialized CourtBuilder.wallThickness also updated, since it overrides the code default). Floor and ceiling footprints overlap the walls so the shell has no corner seams. Net (0.04m) left alone — a rule-neutral obstacle.
3. **Depenetration cap**: ball `maxDepenetrationVelocity` 10 (default) → 3, so a racket-vs-wall squeeze resolves gently instead of firing the ball through the far side.
The `BallEscapeWatchdog` stays as the last-resort net behind all three.

## Why this design

Ball-throwing is a strongly VR-native interaction; wall-bounce physics is nearly free via Unity's built-in engine; the fault-rule logic is simple; the AI-opponent problem is genuinely interesting but tractable, not research-level; and grounded movement avoids locomotion/comfort-tuning risk. Treat the "Explicitly out of scope" list above as deliberate, not incidental — don't reintroduce any of it without the human explicitly asking.
